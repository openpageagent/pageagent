# 邮件通知

浏览器插件无法直接建立 SMTP 所需的 TCP/TLS 连接，因此复用插件与现有 MCP Server 的 WebSocket 通道，由 MCP Server 使用 Nodemailer 发送邮件。没有新增 MCP 工具或其他服务进程。

邮件账户在插件「连接配置 → 邮件通知」中配置，位于 MCP 连接日志下方，只保存一份。发送时，插件将本次账户配置、正文、收件人和附件传给已连接的 MCP Server；服务端仅用于当前发送，不落盘保存账户，不记录密码或邮件内容。

「启用邮件通知」是总开关，默认开启，切换后立即保存。关闭后禁用测试发送、跳过流程结束通知，并拒绝邮件节点发起的新发送；账户配置仍可编辑和保存。已经提交的邮件不会撤回。开关下方统一显示「已就绪」「已关闭」或「未连接 MCP Server，暂不可用」。

## SMTP 配置

支持标准 SMTP，可自定义服务器和端口，使用 TLS 或 STARTTLS 加密连接。当前支持用户名与密码、授权码或应用专用密码认证；免认证服务器可同时留空用户名和密码。暂不支持 OAuth2 认证或不加密的 SMTP 连接。

1. 按邮件服务商的说明开启 SMTP 服务，获取服务器地址、端口、加密方式及认证信息。
2. 启动包含邮件发送功能的 MCP Server。源码运行先在 `mcp-server/` 中执行 `npm install`，再按现有方式运行 `node index.js`；使用发布单文件的用户需更新服务端文件。
3. 在插件「连接配置」启用 MCP 服务器连接，默认 `ws://127.0.0.1:9999`。开关上方的「MCP 连接与使用说明」折叠面板提供启动命令和客户端配置说明。远程连接须使用 `wss://`，可在服务端前配置 TLS 反向代理，保留 WebSocket 的 Origin 头。
4. 在「连接配置 → 邮件通知」填写以下信息并保存。

| 配置 | 填写说明 |
| --- | --- |
| SMTP 服务器 | 服务商提供的主机名或 IPv4 地址，如 `smtp.example.com`，不含协议和端口 |
| 端口 | 按服务商要求填写；TLS 通常为 `465`，STARTTLS 通常为 `587` |
| 加密方式 | `TLS` 或 `STARTTLS`，须与服务器端口匹配 |
| SMTP 用户名 | 服务商提供的用户名，通常是完整邮箱地址 |
| SMTP 密码 / 授权码 | 服务商要求的 SMTP 密码、授权码或应用专用密码 |
| 发件邮箱 | 该 SMTP 账户允许使用的发件地址 |
| 发件人名称 | 默认 `Page Agent`，留空时也使用该名称 |

例如 QQ 邮箱使用 `smtp.qq.com`、`465` 端口和 `TLS`，用户名填写完整 QQ 邮箱地址，密码填写开启 SMTP 服务后取得的授权码（不是 QQ 登录密码）。

邮件配置可离线保存。测试邮件、流程结束通知和邮件节点均需要已连接且握手确认支持邮件发送的 MCP Server；页面会显示连接状态并禁用不可用的测试发送按钮。旧版服务端需要更新后重新连接。

点击邮件配置旁的「发送测试邮件」打开抽屉，在抽屉中指定收件人、抄送、密送和选择本地附件，再点击底部的发送按钮。发送使用当前表单配置，不自动保存账户配置，结果显示在抽屉中。成功提示仅表示 SMTP 接受邮件，请自行查看收件箱。

## 配置备份与恢复

「一键导出所有数据」包含可选的「邮件通知」模块，导出总开关及已保存的 SMTP 服务器、端口、加密方式、用户名、密码／授权码、发件邮箱和发件人名称。从未保存邮件配置、也未切换总开关时，该模块显示无数据；仅切换过总开关的空账户也可备份恢复。备份中的密码／授权码为明文，导出列表会明确提示。

「一键导入备份数据」勾选「邮件通知」后，会校验配置并覆盖当前唯一的 SMTP 发件账户，配置页同步更新。导入可离线完成，不会发送测试邮件；未勾选或旧版 v6 备份不包含该模块时，现有邮件配置保持不变。测试抽屉中的临时收件人和文件不进入备份，流程结束通知配置和邮件流程节点随流程模块备份。

## 整个流程的结束通知

在「流程」编辑页点击「保存流程」与「校验」之间的「流程通知」，打开同名抽屉。分别勾选「成功时通知」「失败时通知」，填写收件人、主题和正文。点击「确定」时，若有修改，会提示点击「保存流程」；未修改则直接关闭。取消抽屉不会修改配置。两个开关默认关闭，启用任意一项时必须填写有效的固定收件邮箱；多个地址用逗号、分号或空白分隔，最多 100 个。发件账户复用上面的 SMTP 配置。

通知在整个 Flow 的运行结果确定后发送，中途节点失败导致流程终止也能通知，无需额外添加邮件节点。数据集、多轮执行和自动重试都汇总到本次运行结束时的一封通知，成功／失败与运行报告一致。主动停止、单节点调试不发送结束通知。流程组中的每个 Flow 按自身配置通知。

主题和纯文本正文会预填可编辑的默认模板，包含流程名称、结果、流程 ID、运行编号、触发方式、起止时间（UTC）及失败原因。旧配置未填写主题或正文时也使用默认模板。支持与流程节点相同的变量语法：

| 写法 | 内容 |
| --- | --- |
| `{{input.名称}}` | 运行入参中的「名称」 |
| `{{report.summary}}` | 节点输出变量 `report` 的 `summary` 字段 |
| `{{json report}}` | 将节点输出变量 `report` 写成 JSON |
| `{{notification.flowLabel}}` | 流程名称 |
| `{{notification.statusLabel}}` | 成功／失败；`notification.status` 为 `success`／`failed` |
| `{{notification.error}}` | 失败原因，成功时为空 |
| `{{notification.flowId}}`、`{{notification.runId}}` | 流程 ID、运行编号 |
| `{{notification.trigger}}` | 触发方式 |
| `{{notification.startedAt}}`、`{{notification.endedAt}}` | 开始、结束时间（UTC） |

例如将正文改为：

```text
流程：{{notification.flowLabel}}
结果：{{notification.statusLabel}}
摘要：{{report.summary}}
```

变量取流程结束时的值，多轮运行取最后一轮；失败时尚未生成的变量按普通插值输出空字符串，`{{json 变量名}}` 输出 `null`。`notification` 是通知专用变量，不修改流程上下文。模板只插值一次，变量内容里的模板标记不会再次展开。

通知开关、收件人和内容模板在每次运行开始时读取，运行中修改配置从下次运行生效。主题不能为空、包含控制字符或超过 998 字符；纯文本正文最多 1MB，发送前也会校验插值后的内容。Agent 可通过 Flow 资源的 `mailNotification.subject` 和 `mailNotification.body` 配置同一套模板。

流程完成后异步发送通知，不等待邮件投递才结束运行；流程组可继续执行下一步。投递结果返回后记录运行日志，并补写到对应运行报告；通知失败不改变流程的成功／失败结果，不自动重发。启动阶段失败也会尝试发送失败通知，结果记录在会话日志中。

## 流程节点

在「输出与集成」添加「邮件通知」（`sendEmail`）节点。发件账户统一读取「连接配置 → 邮件通知」中保存的账户，收件人、抄送、密送分别由每个节点配置。邮箱地址可用逗号、分号、空格或换行分隔；三项至少填一项，合计最多 100 个地址，实际投递按完整地址去重。密送地址只进入 SMTP 信封，不写入邮件头。

主题、收件地址、正文和附件字段支持 `{{变量}}`。正文可选纯文本或 HTML，最大 1MB；HTML 正文按输入发送，动态内容需自行进行 HTML 转义。

附件字段填写 JSON 数组，最多 20 个，解码后总大小最多 20MB：

```json
[
  {"fileName":"report.json", "content":"{{json report}}"},
  {"fileName":"image.png", "contentMode":"base64", "content":"{{imageBase64}}", "mimeType":"image/png"}
]
```

文本附件使用 UTF-8。Base64 只填写编码内容，不带 `data:` 前缀；`mimeType` 可选，省略时由 Nodemailer 按文件名推断。也可用 `{{json attachments}}` 引用完整数组。

附件 JSON 先解析，再对各字段插值，内容里的换行、引号不会破坏 JSON。完整数组模板的结果作为数据使用，不再解释其内部模板标记。

插件不能仅凭任意本地路径读取文件，MCP Server 也不会读取邮件请求中的文件路径或 URL。流程附件应传文本或 Base64 内容；测试入口选择的本地文件由浏览器读取后传输。

WebSocket 请求总大小上限为 32MB，JSON 转义和 Base64 会增大体积；邮件服务器还有自身的 MIME 大小限制。

## 投递结果

成功返回 `{messageId, acceptedCount, rejectedCount: 0}`，表示 SMTP 已接受，不保证邮件最终进入收件箱。部分收件人被拒绝时节点失败，并给出已接受数量、拒收地址和 Message-ID；已接受地址可能已经收到邮件，只应补发拒收地址。

邮件节点不自动重试。排队最长 60 秒，开始发送后的 SMTP 超时为 80 秒，插件等待排队及发送结果的总上限为 150 秒。排队期间断线、取消或服务端关闭会移除等待任务，并释放队列容量；发送期间会关闭当前 SMTP 连接，但不能撤回服务器已经接受的邮件。遇到结果不明确的错误时，先核对投递记录再决定是否补发。

同一个 MCP Server 进程的所有客户端共用邮件调度器：全局最多同时发送 4 封；同一 SMTP 登录账户（忽略首尾空白及大小写，无登录名时使用发件邮箱）只允许发送 1 封。更换主机、端口或 TLS 模式不会绕过同账户串行限制。同账户按入队顺序处理，不同账户可以使用空闲发送名额。

等待队列最多容纳 32 封，等待任务的 JSON 请求内容合计不超过 64MB；这是队列内容限制，不是 Node.js 进程总内存限制。正在发送的邮件不占等待队列容量。队列满或排队超过 60 秒会明确返回“邮件尚未发送”，不会自动重试，也不会落盘排队。这些限制按服务端进程生效，多个独立 MCP Server 进程之间不共享队列。

连接使用内部 WebSocket 帧 `mail.send`、`mail.cancel`、`mail.result`，MCP 仍保持现有六个 ARP 资源方法。同一连接的相同请求 ID 不重复投递。发件配置保存于独立 `mail_settings` 键，不进入公开配置资源，通过一键备份中的「邮件通知」模块导出和恢复。

服务端依赖 Nodemailer 8.0.11，许可证为 MIT-0，兼容当前 Node.js 16+ 要求，无额外运行时依赖。许可证见 `mcp-server/NODEMAILER_LICENSE`，打包时一并复制。
